# 飯製現貨與影片實作規格

本次直接實作已確認需求：同 IP／同名但不同工藝是獨立商品；價格依庫藏統一設定；批次圖片上架、各商品專屬實拍影片；IP 收合與每頁 12 件按需載入。

後續更新：同海報的不同工藝現在會在同一個商品區塊顯示，底層仍保留各工藝自己的 SKU 與庫存。飯製與預購也可反覆按批次結單，只統計已付清訂單；追加安裝與操作方式見 [商品多工藝與分批結單](procurement-rounds.md)。

- 商品以 `inventory_kind=fanmade` 與飯製明細獨立管理，沿用商品 ID 串接現有訂單、付款、包貨。`products.stock` 是唯一實際庫存來源；飯製獨立操作介面及異動紀錄，避免兩套庫存重複扣帳。
- 可售數量為實際庫存減有效訂單未包貨數量。新增／修改訂單明細鎖定商品並檢查可售數量，取消／刪單自動釋放；既有包貨流程扣實際庫存，交易結束時檢查保留量。
- 批次最多 50 張，逐檔壓縮／上傳、個別重試，具穩定批次 ID。影片原檔進私有 bucket，背景 worker 轉成 H.264 MP4 fast-start 與 WebP 封面；只有 ready 影片可公開播放。
- 飯製表單沿用 claim 訂單／客戶及 Turnstile。初始只回傳外觀、價格與 IP 統計；展開 IP 才取 12 款商品與靜態封面，點開才取得該工藝影片 URL。收合不清除購物車。
- 影片 worker 使用 FFmpeg 與服務端金鑰；提供 Dockerfile、租約與失敗重試，舊任務不得覆寫新影片。Vercel 網頁服務不承擔長時間轉檔。
- 舊飯製資料以明確選取商品、確認單一工藝後轉入，保留數量與歷史訂單，不自動複製庫存。

驗收涵蓋資料庫隔離／庫存／同批重試／付款與包貨相容、批次上架、未點播放零影片請求、未展開 IP 零商品媒體請求、分頁與收合保留數量、手機／桌面及完整回歸檢查。

## 安裝到既有專案

此變更包含前端、資料庫及獨立影片處理程序。程式完成不代表正式資料庫或影片服務已安裝；本次沒有修改正式資料庫或發布正式站。

1. 在已套用既有 migrations 的 Supabase 專案，開啟 SQL Editor，貼上並執行完整的 [20261114140129_fanmade_catalog_stock_and_media.sql](../supabase/migrations/20261114140129_fanmade_catalog_stock_and_media.sql)。只執行一次；檔案自帶交易，失敗時整筆回滾。它會沿用既有 claim、付款與包貨資料表，並建立兩個影片 buckets 和 RLS。
2. 使用 Node.js 22 或以上，執行 `npm ci`、`npm run dev`。登入後側邊欄進入「飯製管理」（`/fanmade-management`）。既有 Supabase 網址、公鑰、正式 Turnstile 設定不需另開一組。
3. 先儲存飯製統一價格，再建立飯製表單。在「批量上架」按「文字批量上架」開啟彈跳視窗，填一次批次 IP（例如蜘蛛人），並設定預設工藝與庫存。按「一次選擇多張圖片」或將多張圖片拖入選圖區，再逐圖設定工藝及各工藝的影片。展開後每批最多 50 件商品。
4. 選取表單時，新批次會自動加入該表單；既有商品可勾選加入，也可展開 IP 後整個 IP 加入。按「開放接單」並複製 `/fanmade/{token}` 連結。
5. 安裝下方 worker，影片才會從「等待／轉檔中」變成可公開播放。未設定 worker 時圖片上架及訂購仍可使用，影片會保留在待處理佇列，公開頁不會載入原檔。

舊飯製商品需在管理頁底部指定單一工藝後「確認整筆轉入」。商品 ID、歷史訂單與原有庫存保持一致，並從一般訂購表單移出。若舊商品把多種工藝合在一筆，請先盤點各工藝的實際數量，再調整原商品與新增其他工藝，避免把總數複製到每種工藝。

## 工藝文字批量

「預設工藝」可以一次貼上多種工藝，也可指定各自庫存：

```text
亮銀龍｜10
水波紋｜6
雷射｜3
```

視窗內按「帶入範例」會填入蜘蛛人 IP 及上面的工藝、庫存文字，方便修改成自己的資料；不會上傳假圖片或直接建檔。已有草稿時會先確認，草稿與圖片會保留，需重新套用再核對。關閉或按 Esc 會保留本頁草稿，重開視窗可繼續；上傳／建檔時不可關閉。重新整理前仍應先完成上架，瀏覽器無法保留未送出的圖片與影片 File。已送出待確認批次的請求資料則會保留，可重開視窗沿用同一批重試。

只填工藝名稱會使用預設庫存；也支援 Tab、半形 `|`、名稱後空格加數量，以及純工藝清單 `亮銀龍、水波紋、雷射`。金額仍使用飯製統一價格。

- 「新圖片先帶入預設工藝，再逐圖調整」：新選取的圖片先帶入上方工藝預設。每張圖片各有「本圖工藝（文字批量）」編輯區，可貼上不同清單並按「套用這張圖片工藝」。例如同一 IP 的圖一有亮銀龍、水波紋、雷射三種，圖二只有亮銀龍、水波紋兩種，最後建立五件工藝商品，只上傳兩張圖片。
- 「依圖片順序，一張配一種工藝」：2 張照片配 2 行工藝，第一張配第一行、第二張配第二行，適合每張照片拍攝不同工藝。圖片總數必須和文字列數相同，請一次選齊。同一工藝可以重複列出、設定不同商品的數量。

選圖後會先依圖片分組顯示商品草稿，確認後才按「建立本批飯製商品」。批次 IP 可在選圖後補填，會自動更新空白或沿用舊批次 IP 的列，保留逐列自訂的不同 IP、庫存、圖片與影片，不需重新套用工藝。

批量預覽以「IP → 多張海報 → 各工藝影片」呈現，例如蜘蛛人 IP 下一次選取多張海報，之後可按「繼續加入圖片」追加。追加圖片不會清除已填庫存、已選影片或其他圖片的工藝清單。每張海報的名稱在圖片區填一次，即同步本圖所有工藝；各工藝列主要顯示庫存與專屬影片。只有需要個別例外時，才展開「個別修改IP、名稱或工藝」；既有例外 IP 會沿用並提示。上傳或等待同批重試時，選圖、拖曳與修改均鎖定，避免變動商品和影片的對應。

上方工藝文字、預設庫存及套用方式只用於之後新增的圖片，更改後不會重設已調整好的圖片，也不會因此停用建立按鈕。需要全部圖片重新使用同一份預設時，才按「辨識並套用到本批圖片」；這會取代各圖的工藝與庫存設定，移除工藝或未套用文字草稿前會先提示確認。

每張圖片的工藝清單可使用「工藝｜庫存」，只貼名稱時保留這張圖已有工藝的庫存，新工藝則使用預設庫存。相同工藝保留原影片；新增工藝不會複製其他工藝的影片。移除已選影片的工藝會先確認，取消時保留原草稿。編輯本圖清單後，先套用或按「還原本圖工藝」，再調整下方庫存與影片；其他圖片不受影響。每批上限依實際預覽的工藝商品數合計計算為 50 件。底部會提示哪些圖片尚未套用，避免漏送新工藝。

此功能只處理本批尚未建立的草稿，不會複製既有庫存。逐圖套用與修改工藝不需要新增 migration；已送出的待確認批次仍沿用原請求及商品順序重試。

每工藝的實拍影片需在自己的商品列選取；展開工藝時不會複製其他工藝的影片。批次送出後預設資料與列順序鎖定，重試沿用相同商品內容及圖片。本次文字批量功能沿用已安裝的資料結構，不需要再次執行 migration。

## 影片 worker

瀏覽器以可重試的 TUS 分塊直接上傳 Supabase Storage，原檔上限 100MB，支援 MP4、MOV、WebM。worker 檢查影片內容、最長 120 秒，再產生最長邊 1080 的 H.264／AAC MP4、fast-start 資訊及最長邊 480 的 WebP 封面，播放檔上限 50MB。

建議將此程序部署到可持續運行的 Docker 主機，與 Vercel 網頁分開執行：

```bash
cp scripts/media-worker/worker.env.example .env.media-worker
# 在 .env.media-worker 填入這個 Supabase 專案的網址與伺服器 secret key。
docker build -f scripts/media-worker/Dockerfile -t archive-stock-media .
docker run -d --name archive-stock-media --restart unless-stopped \
  --env-file .env.media-worker archive-stock-media
docker logs -f archive-stock-media
```

`SUPABASE_SECRET_KEY` 僅提供給 worker 的伺服器環境，不可加 `NEXT_PUBLIC_`，不可貼進前端或提交到 Git。也支援既有 `SUPABASE_SERVICE_ROLE_KEY` 作為替代。原檔 bucket 私有，播放 bucket 僅 worker 可寫入；所有公開影片連結只指向完成處理的檔案。

本機已安裝 FFmpeg／ffprobe 時，也可用下列方式測試單一任務；不加 `--once` 會持續輪詢：

```bash
node --env-file=.env.media-worker scripts/media-worker/worker.mjs --once
```

本機建議使用下列命令，會自動讀取 `.env.media-worker`，檢查伺服器金鑰、FFmpeg／ffprobe 及 Supabase 連線，再開始處理。缺少設定或轉檔工具時會先停止，不會把佇列中的影片錯誤標記為失敗：

```bash
npm run media:check
npm run media:worker
```

若沒有設定檔，可從 `scripts/media-worker/worker.env.example` 複製。網址填目前專案的 Supabase URL，`SUPABASE_SECRET_KEY` 填 Secret key，不能填 Publishable／anon key；可在 [Supabase API Keys 設定](https://supabase.com/dashboard/project/_/settings/api-keys/) 取得。金鑰只填本機設定檔，不需貼到聊天。本機測試工具若已安裝在 `.local/media-tools` 會自動使用，也可指定 `FFMPEG_BIN`、`FFPROBE_BIN`。

影片上傳成功仍需完成轉檔。管理頁會分別顯示「已上傳，等待轉檔」、「背景轉檔中」、「已轉檔」；長時間停在排隊中時，先確認 worker 正在運行。只有轉檔完成、已加入表單且開放中的工藝商品，客人才會看到實拍按鈕。客人點擊前仍不會載入影片原檔或播放檔。

每個任務有 5 分鐘租約，程序中斷後會由後續 worker 接手，最多 3 次租約。處理失敗可在管理頁按「重試影片轉檔」，沿用原檔並建立新任務；也可重新上傳取代。每次租約輸出使用獨立路徑，過期任務無法覆蓋新檔。管理頁按「重新載入」更新狀態。

目前保留原檔及被取代任務的輸出，方便重試與追查；需依實際容量定期清理已不再使用的檔案。worker 本機暫存會在每次處理後刪除。

## 庫存與金額

- 一件工藝是一個商品 ID，例如「蜘蛛人／夜景｜亮銀龍」與「蜘蛛人／夜景｜水波紋」，可各自有 10 張與 6 張。
- 實際庫存是現貨總量；有效待包訂單尚未包貨的數量為預留；可售 = 實際 − 預留。新訂單鎖定商品後驗證可售量，取消或刪除未完成訂單會釋放預留，包貨完成才扣實際庫存。
- 調整庫存不可低於預留量，必須填調整原因，異動保留在 `fanmade_stock_movements`。
- 統一售價直接用於表單，不加一般商品的 150 元。調價同步現有飯製商品及表單，歷史訂單的明細快照保留原成交金額。舊頁面送單時若價格已變更會要求重新整理；已成功訂單的同一請求重試仍回傳原收據。

## 載入行為與驗證

客人看到的飯製表單沿用一般訂購表單的商品、已選明細與總額排版，桌面左側選商品、右側填聯絡資料，手機改為單欄。售價只顯示一次。商品封面作為影片入口，可在「選擇實拍工藝」切換同海報各工藝的封面，再點擊觀看對應商品的實拍；每種工藝的訂購數量仍分開選擇。影片尚未備妥時顯示「實拍影片準備中」，庫存足夠的商品仍可訂購。這次介面更新不需新增 migration。

公開頁初始只有外觀、統一價格及 IP 名稱／數量。IP 預設全部收合；展開才取得 12 款商品及各款完整工藝選項、靜態封面，按「載入更多」取得下一頁。同一商品的工藝不會被分到不同頁。收合或搜尋其他 IP 會保留已選數量；不同 IP 可以合併送出同一張訂單。切換實拍工藝不請求影片，卡片不建立 video 元素，只有點擊封面才查詢該工藝的播放網址，且播放器設為 `preload="none"`；關閉時暫停並卸載影片。客人表單的封面不再提供圖片放大入口。

```bash
npm run typecheck
npm run lint
npm test
npm run test:fanmade-ui
npm run test:media
npm run build
```

`test:fanmade-ui` 需要本機 Chrome（macOS 預設路徑已設定，可用 `PLAYWRIGHT_CHROME_PATH` 指定其他安裝位置）；`test:media` 需要 `ffmpeg`、`ffprobe`，或透過 `FFMPEG_BIN`、`FFPROBE_BIN` 指定執行檔。

資料庫測試在 PGlite 執行新 migration，載入既有商品建立、公開送單、claim 訂單投影及包貨函式，驗證庫存、付款同步、價錢快照、重試、RLS、分頁、舊資料轉入與影片租約。瀏覽器測試以實際 React 元件搭配控制的 API 回應，驗證 375／768／1440px、延後載入、載入失敗重試、數量保留、送單收據及批次圖片不重傳。影片測試會實際產生 MOV 並轉為 MP4／WebP，驗證 fast-start 與損壞檔案拒絕。以上測試不會寫入正式 Supabase。

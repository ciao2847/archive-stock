# 預售訂購與配單接入包貨

2026-10-20 已依使用者指示，將遷移套用至目前連線的 Supabase 專案；網站程式未部署。已補建 58 筆預售正式訂單，無缺少商品對應或金額、付款狀態不一致的訂單。套用前後比對確認原始訂購、既有訂單及商品庫存未改動。

## 使用方式

1. 目前連線專案已套用 `supabase/migrations/20261020033449_connect_claims_to_packing.sql`，不需重複執行；其他環境應先在測試資料庫驗證。
2. 客人送出預售表單後，自動建立同確認編號的正式訂單。既有訂購會在遷移時補建。
3. 訂單管理搜尋確認編號，選擇訂購，可看到包貨狀態、已包／總件數並按「開始包貨」。
4. 已確認配單先按「對應出貨商品」，填寫實際庫存商品、數量、單價；合計必須等於原配單總額。完成後使用相同包貨入口。
5. 已到貨商品可以分批掃碼包貨。沿用既有包貨工作、QR 標籤及庫存扣除流程，未到貨品項保留。

正式訂單是來源訂購的出貨紀錄：保留原確認編號，一對一建立，不另收一次款。收款與撤銷仍在來源帳務操作，同步正式訂單付款狀態。部分付款仍是未付清，不會轉成全額已付。

預售轉單及配單商品對應不會扣庫存、改成現貨或強制要求現貨足量；實際完成包貨才沿用原系統扣庫存。

已開始掃描、包貨或結算後，不能改出貨品項與數量。來源不能在已履約後刪除；正式訂單不能獨立刪除或改寫來源帳款。配單完成實際包貨後，同步既有入出庫核對欄位，不能再用舊核對按鈕繞過庫存處理。

## 舊資料與限制

- 已確認配單會補建正式訂單，但圖片名稱不會被猜成庫存商品；需人工對應商品。
- 已有出貨核對的歷史配單會保留為已出貨，不能再次包貨。
- 預售明細的商品已移除或不屬於該庫藏時，保留訂單但不建立不完整出貨品項；介面提示確認商品資料。
- 既有手動建立的一般訂單無法僅憑電話、商品或金額安全推斷是否對應某筆預售；上線前需核對這類人工重複紀錄。
- 尚未套用遷移時，一般訂單查詢仍可使用，但新來源的包貨與配單商品對應尚不能啟用。

## 驗證

`npm test` 包含獨立 PGlite PostgreSQL 測試，使用隔離的基礎結構、真實既有包貨遷移及本次遷移，覆蓋補建、防重複、來源付款同步、配單金額檢核、分批包裝、重試不重扣庫存與來源操作保護。它不連接 Supabase 專案，不等於完整 Supabase 堆疊測試。

`node tests/browser/order-sources.browser.mjs` 使用實際 React 元件及隔離 API fixtures，驗證手機與桌面搜尋、訂購匯款、預售包貨入口、配單商品對應、金額錯誤與映射後進入包貨的回呼。
